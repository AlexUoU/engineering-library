# 把工具设计成清楚的行动接口

主题：工具设计、MCP 与 Skills

编辑版：1.1 · 2026-10-16

来源：https://www.anthropic.com/engineering/writing-tools-for-agents

## 先抓住这个问题

助手面前有几个名称相近的搜索工具，参数只有含糊的 q，返回结果又缺少稳定文档编号。选错工具或引用错资料，未必是模型不理解任务，也可能是接口让正确行动变得困难。怎样设计一个足够清楚、又不过度暴露细节的工具？

## 理解方法

工具应表达真实任务，参数和返回值要有意义。让模型容易选对工具、理解结果并在出错时修正。

## 适用边界

把每个底层接口全部暴露并不一定更好。简短返回也不能省略完成任务必需的标识和证据。

## 换个场景想想

【原创演练】把含糊的 find(q) 改写为资料搜索契约：查询、可选日期范围、结果数量、稳定文档编号、摘要、来源和下一页入口。再设计“没有结果”和“同名文档”两个场景。

## 把它带回自己的工作

选一个你正在做的小任务，写下能借鉴的一点、暂不适用的一点，以及验证效果需要观察的证据。案例与练习均为本学习库原创，用于迁移理解，不代表来源文章的实验结果。

## 可选回想

1. 暂时合上导读：用自己的话说明这篇文章要解决什么问题，以及它的主要方法。

2. 一个资料搜索工具需要哪些返回字段，才能支持后续可靠引用？

3. 这篇方法有什么适用边界？你会怎样检查它在自己的任务中是否有效？

## 对照要点

1. 文章强调工具选择、命名、说明和返回信息都影响 Agent 表现，并用任务评测迭代工具设计。工具应表达真实任务，参数和返回值要有意义。让模型容易选对工具、理解结果并在出错时修正。

2. 应有稳定标识、相关摘要、来源与必要的分页信息；解释字段如何支持选择和引用，并测试歧义场景。

3. 把每个底层接口全部暴露并不一定更好。简短返回也不能省略完成任务必需的标识和证据。
